## 1. 文档目的

本计划用于指导 Accounting Assistant 的第一轮界面视觉升级。

本轮工作的核心目标是在不改变现有业务流程、不迁移技术栈的前提下，将当前接近 WPF 默认样式的界面升级为清晰、可信、高效的现代 Windows 桌面生产力工具。

本计划只覆盖界面设计与交互表现，不处理 OCR 精度、语义解析质量、Excel 数据规则或 Python 运行环境安装。

## 2. 项目现状

### 2.1 技术与界面构成

- 技术栈：C#、.NET 10、WPF。
- 主窗口：`MainWindow.xaml`。
- 全局资源：`App.xaml`，目前没有应用级设计资源。
- 业务弹窗：
  - `BatchFillDialog.xaml`
  - `EditOcrTextDialog.xaml`
  - `ExcelExportReviewDialog.xaml`
  - `SuggestionManagerDialog.xaml`
- 当前核心布局：左侧票据队列、中间票据预览、右侧审核面板、顶部命令区、底部审核操作区。

### 2.2 当前优势

- 三栏结构符合票据审核工作流。
- OCR、字段审核和票据图片处于同一工作空间，减少窗口切换。
- 已有明确的业务阶段和快捷键。
- 核心功能完整，适合采用渐进式视觉升级。

### 2.3 当前视觉问题

- 大部分控件使用 WPF 默认外观，产品辨识度较低。
- `App.xaml` 没有统一颜色、字体、间距、圆角和控件状态。
- 颜色、尺寸和边距分散硬编码在各个 XAML 文件中。
- 顶部所有操作按钮权重接近，主次关系不清晰。
- `GroupBox`、默认 Tab 和默认列表样式使界面偏传统工具软件。
- Pending、Processing、Review、Approved 和 Error 的状态表达不够系统。
- Hover、Pressed、Focus、Selected、Disabled 等交互反馈缺少统一规范。
- 空状态、处理中状态和错误状态缺少完整的视觉呈现。
- 主窗口和业务弹窗没有共享统一的视觉语言。

## 3. 设计判断

### 3.1 产品定位

Accounting Assistant 是面向财务审核人员的 Windows 桌面生产力工具。界面需要支持长时间、高频率、低误操作的审核工作。

### 3.2 设计语言

采用克制的 Fluent 风格作为方向参考，但不引入 Web Fluent UI，也不迁移现有 WPF 技术栈。

设计关键词：

- 可信
- 清楚
- 高效
- 安静
- 精确
- 可持续使用

不采用以下方向：

- 大面积渐变或霓虹发光
- 玻璃拟态堆叠
- 装饰性复杂动画
- 营销网站式超大标题
- 过度留白导致信息效率下降
- 为视觉效果重写现有工作流

### 3.3 设计参数

- `DESIGN_VARIANCE: 3`
  - 保持稳定、可预测的生产力工具布局。
- `MOTION_INTENSITY: 2`
  - 只使用悬停、按压、焦点和必要状态切换反馈。
- `VISUAL_DENSITY: 7`
  - 保持较高信息密度，同时提升可扫描性。

### 3.4 主题策略

第一轮只完成高质量浅色主题，不在同一阶段同时开发深色主题。

原因：

- 当前应用尚无设计 token，先稳定单一主题能降低改造风险。
- OCR 图片和票据白底在浅色工作区中更自然。
- 财务审核场景更重视清晰度和打印材料一致性。

深色主题可以在设计 token 稳定后作为独立阶段追加。

## 4. 改造原则

1. 保留现有技术栈，不引入 React、Tailwind 或 WebView。
2. 保留业务流程、按钮语义、快捷键和事件绑定。
3. 不静默修改字段顺序、审核规则、导出规则和状态机。
4. 优先建立设计系统，再修改具体页面。
5. 样式集中管理，减少控件上的硬编码颜色和尺寸。
6. 每一阶段保持可编译、可运行、可回退。
7. 每次只处理一个清晰范围，避免界面和业务逻辑同时大改。
8. 所有重要操作必须具备可见的键盘焦点和禁用状态。
9. 动画只用于反馈状态变化，不用于装饰。
10. 不牺牲信息密度来追求营销页面式视觉效果。

## 5. 目标界面结构

### 5.1 顶部命令栏

将当前两行默认按钮整理为清晰的命令栏：

- 输入组：选择图片、选择文件夹。
- 处理组：分析当前、分析全部。
- 批量组：批量填写、导出 Excel。
- 右侧状态区：Worker 状态、当前进度或最近操作结果。

视觉规则：

- 同组操作靠近，不同组之间使用间距或轻量分隔。
- 常用操作和高影响操作采用不同按钮级别。
- 导出不与普通分析操作混成同一视觉权重。
- 禁用状态仍需清楚可读，不能只降低到接近不可见。

### 5.2 左侧票据队列

保留队列位置，重新设计列表项：

- 文件名作为主要信息。
- 阶段名称作为次要信息。
- 状态颜色只表达真实业务状态。
- 当前选中项有明确的背景、边框或强调条。
- 多选状态与单选焦点状态可区分。
- 队列底部保留排序操作，但降低其视觉权重。

建议增加的视觉信息：

- 当前票据序号和总数。
- 各阶段的统一状态标签。
- 处理中状态的轻量活动反馈。

### 5.3 中间票据工作区

票据图片继续作为界面视觉中心：

- 使用中性工作区背景衬托白色票据。
- 图片边缘使用轻量阴影或边框区分层级。
- 保留现有缩放和 OCR 覆盖层逻辑。
- OCR 选中框、普通框、低置信度框使用统一状态色。
- 空工作区提供明确的导入引导，而不是只显示空白区域。

### 5.4 右侧审核面板

将传统 `GroupBox` 视觉转换为现代 Inspector 面板：

- 面板标题显示当前票据名称和阶段。
- OCR 与 Fields 使用清晰、紧凑的分段切换。
- OCR 列表强化文字、置信度、修正状态之间的层级。
- 字段标签位于输入控件上方或采用更稳定的双列对齐。
- 冲突警告不仅依赖红色边框，还需要图标或文字说明。
- Debug Dump 继续折叠，并在视觉上与日常审核功能隔离。

### 5.5 底部操作栏

底部操作用于表达当前票据的审核进度：

- `Next Receipt`：次级操作。
- `Confirm OCR`：当前处于 OCR Review 时的主操作。
- `Approve Fields`：当前处于 Field Review 时的主操作。
- 同一时刻只突出一个符合当前阶段的主要操作。
- 快捷键以低干扰方式显示在按钮或辅助文本中。
- 冷却期间显示原因，避免按钮突然失去响应感。

## 6. WPF 设计系统规划

### 6.1 建议文件结构

```text
app/AccountingAssistant.App/
  Styles/
    DesignTokens.xaml
    ControlStyles.xaml
    DialogStyles.xaml
  App.xaml
  MainWindow.xaml
  BatchFillDialog.xaml
  EditOcrTextDialog.xaml
  ExcelExportReviewDialog.xaml
  SuggestionManagerDialog.xaml
```

如果拆分 ResourceDictionary 导致第一阶段改动过大，可以先使用两个文件：

```text
Styles/DesignTokens.xaml
Styles/ControlStyles.xaml
```

弹窗样式在第二阶段稳定后再单独拆分。

### 6.2 设计 token

需要集中定义：

- `Color`：背景、表面、边框、文字、强调色和语义状态色。
- `SolidColorBrush`：所有常用颜色的画刷资源。
- `FontFamily`：优先使用 `Segoe UI Variable Text` 和系统回退字体。
- `FontSize`：标题、面板标题、正文、辅助文字和数据文字。
- `Thickness`：统一的 4、8、12、16、24 间距体系。
- `CornerRadius`：输入控件、按钮、面板和弹窗的统一规则。
- 控件高度：紧凑、标准和主要操作三档。
- 阴影：只用于浮层、弹窗和票据纸张等真实层级。

### 6.3 推荐色彩方向

最终颜色应在实际截图中确认，初始方向如下：

- 应用背景：冷灰白。
- 主表面：接近白色。
- 次表面：浅冷灰。
- 主文字：深蓝灰，不使用纯黑。
- 次文字：中性灰蓝。
- 主强调色：克制的蓝色。
- 成功：低饱和绿色。
- 警告：琥珀色。
- 错误：低饱和红色。
- 处理中：强调蓝色。

强调色只用于：

- 当前主要操作
- 选中状态
- 键盘焦点
- 真实进行中的状态

### 6.4 控件样式范围

第一轮需要统一：

- Window
- Button
- TextBox
- ComboBox
- ListBox
- ListBoxItem
- TabControl
- TabItem
- CheckBox
- Expander
- ScrollBar
- ToolTip
- 状态标签
- 对话框底部按钮区

每个交互控件至少需要：

- Normal
- Hover
- Pressed
- Focused
- Disabled
- Selected 或 Checked（适用时）
- Validation Error（适用时）

## 10. 风险与控制措施

### 10.1 WPF 控件模板复杂度

风险：完整重写 ComboBox、TabControl 或 ScrollBar 模板可能破坏键盘、弹出层或禁用行为。

控制：优先使用 Setter 和局部模板，复杂控件逐个验证，不在同一提交中同时替换所有模板。

### 10.2 XAML 资源引用错误

风险：资源加载顺序或键名错误可能导致应用启动失败。

控制：DesignTokens 先加载，ControlStyles 后加载；每次新增资源后立即编译和启动。

### 10.3 业务事件被视觉重构破坏

风险：重排控件时丢失 `x:Name`、Click、SelectionChanged 或快捷键绑定。

控制：保留控件名称和事件签名，建立事件绑定核对清单。

### 10.4 高信息密度下的空间不足

风险：增加间距后，右侧字段区和顶部命令区可能发生拥挤。

控制：使用紧凑的 4/8/12 间距体系；先保证信息完整，再进行视觉留白。

### 10.5 视觉调整引入过多代码改动

风险：界面改造与 `MainWindow.xaml.cs` 重构混在一起，难以回归。

控制：本轮不主动拆分业务架构；视觉资源、主窗口和弹窗按阶段独立提交。

## 11. 完成定义

满足以下条件后，本轮 UI 视觉升级才算完成：

- 主窗口和四个弹窗使用统一设计系统。
- 主要、次要和危险操作层级明确。
- 所有核心交互控件具备 Hover、Pressed、Focused 和 Disabled 状态。
- 所有业务阶段具备一致的视觉表达。
- Empty、Loading 和 Error 状态可用。
- 默认、最小和高 DPI 环境下布局正常。
- 快捷键、事件绑定和业务流程未发生回归。
- Debug 和 Release 编译通过。
- 文档和截图与新界面一致。

## 12. 推荐执行顺序

实际开发按以下顺序推进：

1. 完成阶段 0，建立截图和回归基线。
2. 完成阶段 1，建立设计 token 和控件样式。
3. 暂停一次，查看主窗口第一版真实效果并校准颜色、密度和圆角。
4. 完成阶段 2，重构主窗口视觉层级。
5. 完成阶段 3，统一全部弹窗。
6. 完成阶段 4，补全状态、键盘与高 DPI。
7. 完成阶段 5，执行最终回归和文档更新。

第一轮实施应从阶段 0 和阶段 1 开始，不直接对 `MainWindow.xaml` 进行大面积零散美化。
